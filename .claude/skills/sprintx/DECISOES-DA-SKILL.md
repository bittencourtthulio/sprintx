# Decisões tomadas na construção da skill sprintx

Ambiguidades do prompt de especificação resolvidas pela opção mais conservadora, uma linha de contexto cada.

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DS-01 | O prompt não define onde a F5 registra o resultado da auditoria, mas a máquina de estados precisa detectar "auditoria aprovada" pelo disco | A F5 escreve `docs/<slug>/00-AUDITORIA.md`; "aprovada" = o arquivo existe e contém a linha literal `VEREDITO: SIM` | Detecção pelo disco exige artefato; formato literal torna o portão binário |
| DS-02 | O prompt diz que ALTA volta para F3, mas não diz o que MÉDIA/BAIXA fazem no veredito | Veredito NÃO se e somente se existir achado ALTA; MÉDIA e BAIXA ficam registrados e não bloqueiam | É a única regra dura dada ("ALTA manda voltar"); bloquear por MÉDIA criaria regra nova não especificada |
| DS-03 | O prompt não define quando um PENDENTE é "bloqueante" | Todo PENDENTE é bloqueante por padrão; só vira não bloqueante com autorização explícita do usuário, com a premissa assumida registrada | Opção mais conservadora: na dúvida, trava a F3 em vez de planejar sobre suposição |
| DS-04 | Critério de detecção do modo EXTERNO vs INTERNO na F1, e o caso ambíguo | EXTERNO quando a feature nomeia ou depende de produto/API de terceiro; ambíguo = ingerir os dois lados; no EXTERNO ingerir também o mínimo interno tocado | Ingerir a mais é conservador; ingerir a menos gera plano cego |
| DS-05 | Quando criar `docs/<slug>/` e `00-BLOQUEIOS.md` (a estrutura os lista, mas nenhuma fase os cria explicitamente) | O scaffold (pasta, `00-BLOQUEIOS.md` vazio, `base/00-INDICE.md`, `base/00-LACUNAS.md`) é o primeiro passo da F1 | F1 é a primeira fase que escreve em disco; ter `00-BLOQUEIOS.md` desde o início garante que ele exista quando a F6 precisar |
| DS-06 | Tensão entre "a skill executa a fase pendente em vez de obedecer fora de ordem" (PARTE 1) e "os commands devem recusar execução fora de ordem e apontar qual fase falta" (PARTE 2) | Os commands de fase recusam a fase pedida, apontam a que falta e executam a fase pendente | Concilia os dois trechos sem violar nenhum: recusa + aponta + segue o método |
| DS-07 | Reexecutar via command uma fase já concluída (ex.: `/sprintx-base` com base pronta) | Permitido só como complemento/revisão a pedido explícito, com aviso de que artefatos posteriores podem ficar desatualizados; caso contrário, executa a fase realmente pendente | Evita regeração destrutiva acidental de trabalho já auditado |
| DS-08 | Idioma dos arquivos da skill | Todo o conteúdo em pt-BR, inclusive a description do frontmatter | Prompt, marca e usuário são pt-BR; a description dispara igualmente bem no idioma do usuário |
| DS-09 | Como obter a data exigida no status das tasks na F6 | Sempre via `date +%Y-%m-%d` do sistema, nunca de memória | Data de memória do modelo pode estar errada; comando é verificável |
| DS-10 | O prompt manda a F6 rodar sem perguntas, mas não diz o que fazer quando não resta nenhuma task executável (tudo bloqueado) | Encerrar com o relatório final, com os bloqueios como pauta — nunca esperar resposta no meio da execução | "Nunca parar e esperar" é a regra dura; encerrar com relatório é a única saída compatível |
| DS-11 | Reauditoria (F5 rodada de novo após retorno à F3) | Sobrescreve `00-AUDITORIA.md`; histórico fica a cargo do versionamento do repositório | Um único arquivo mantém a máquina de estados simples e o portão inequívoco |
| DS-12 | A única pergunta permitida fora da F2 | Na F3, ao detectar algo que exigiria decisão humana em execução, a skill pergunta na hora e registra como nova linha D-NN — conforme o prompt ("transforma em decisão e pergunta na hora") | Está na especificação da F3; registrado aqui porque parece exceção à regra "só a F2 pergunta" |
| DS-13 | Marcadores de preenchimento nos templates | Padrão `{{assim}}` em todos os assets, com nota no topo mandando substituir tudo | Marcador inequívoco, fácil de grepar por vazamento |
| DS-14 | Ordem de execução com múltiplas sprints na F6 | Sprints em ordem numérica estrita; paralelismo só existe onde o plano declarou (entre fases/tasks) | O prompt só declara paralelismo em task e fase; entre sprints, sequencial é o conservador |
| DS-15 | A `description` do frontmatter é "texto voltado a humano" (grafia sprint^x) ou "frontmatter" (grafia sprintx)? | Frontmatter inteiro, inclusive descriptions, usa só a forma `sprintx`; `sprint^x` fica restrito ao corpo dos textos | O item 8 da verificação do prompt é explícito: em frontmatter só pode existir a forma sprintx |
| DS-16 | Achado de auditoria (verificação ponta a ponta): a regra 10 do SKILL.md ("F2 é a única fase que pergunta") contradizia a exceção da F3 (pergunta na hora para decisão nova) | Reescrita a regra 10 para declarar explicitamente a exceção da regra 11, e a regra 11 para citar a exceção — sem depender de DS-12 para reconciliar | Um agente seguindo só o SKILL.md (sem ler este arquivo de decisões durante a execução) não pode ficar em dúvida sobre uma pergunta legítima da F3 |
| DS-17 | Achado de auditoria: nenhum arquivo dizia onde `docs/<slug>/` é ancorado em um monorepo | Adicionada seção "Onde fica docs/<slug>/" no SKILL.md: raiz do repositório Git mais próxima; sem `.git` em nenhum ancestral, raiz do diretório de trabalho; reaproveitar `docs/` existente na raiz antes de criar um novo | Evita que o agente crie `docs/<slug>/` dentro de um workspace individual de um monorepo por falta de instrução |

## Ajuste expx-schema v1 (frontmatter para o painel de operação)

Ambiguidades e conflitos do prompt de ajuste. Regra de ouro aplicada: onde o prompt conflita com a skill, **a skill vence** e o conflito é registrado aqui.

| # | Ambiguidade / conflito | Decisão tomada | Motivo |
|---|---|---|---|
| DS-18 | **Conflito prompt × skill:** o exemplo de `kind: tasks` no prompt traz `arquivos: [a.ts, b.ts]` (lista plana), mas o contrato de task do `SKILL.md` e o `TEMPLATE-tasks.md` já definem `arquivos` como mapa `cria:` / `altera:` | Mantida a forma da skill: `arquivos` é mapa com `cria` e `altera`, cada um uma lista | Regra de ouro (a skill vence) + item 5 da verificação, que exige os mesmos campos do contrato já definido; achatar a lista perderia a distinção cria/altera, que a F5 usa para detectar paralelismo falso |
| DS-19 | **Conflito prompt × skill:** o prompt usa ids de fase `F-01`, `F-03`; a skill já usa `F-NN.M` (`F-01.1`) em `TEMPLATE-fases.md`, `TEMPLATE-sprint.md` e no ORQUESTRADOR | Mantido `F-NN.M` em `fases:`, `fase:`, `paralela_com:` e `caminho_critico:` | Regra de ouro; trocar o id quebraria a correspondência entre YAML e prosa nos arquivos que a skill já gera |
| DS-20 | O prompt lista `estagio: f1..f6` e ids de fase `F-NN.M` sem dizer que são coisas diferentes; um parser poderia confundi-los | Documentada a distinção explicitamente no `00-schema.md`: `estagio` é a fase da máquina de estados; `F-NN.M` é o id de fase do plano; namespaces distintos | Duas grandezas com nome parecido no mesmo contrato é a origem clássica de bug de parser |
| DS-21 | O prompt define `status` de trabalho/sprint/fase (masculino) e de task (feminino), mas o `kind: decisoes` tem `status: fechada \| pendente`, que não está em nenhum dos dois enums | Tratado como enum próprio do kind `decisoes`, documentado como tal | É o único valor possível dado o exemplo do prompt; registrar evita que alguém "corrija" para `concluido` |
| DS-22 | A PARTE 1 exige frontmatter em `00-BLOQUEIOS.md` e `base/00-INDICE.md`, e a PARTE 4 exige template para todo arquivo listado — mas a skill não tinha template para nenhum dos dois (a F1 os criava inline) | Criados `assets/TEMPLATE-BLOQUEIOS.md` e `assets/TEMPLATE-base-indice.md`, referenciados na F1 e na tabela do `SKILL.md` | Sem template, a PARTE 4 ficaria descumprida para dois dos sete kinds; o conteúdo em prosa dos dois é exatamente o que a F1 já mandava escrever |
| DS-23 | O prompt não diz o valor inicial de `concluida_em` e `suite` para uma task recém-planejada na F3 | `concluida_em: null` e `suite: nao_executada` na F3 | Regra 6 do contrato (nunca omitir chave) + `nao_executada` é literalmente o estado de uma suíte que não rodou |
| DS-24 | O prompt não diz o que fazer quando a prosa de uma pasta antiga não permite inferir um valor na migração | Usar `null` (ou `[]`), nunca inventar, nunca perguntar, nunca parar; a chave sempre existe | Coerente com a regra 8 (dúvida vira bloqueio, não pergunta) e com a regra 6 do contrato; inventar valor entregaria dado falso ao painel |
| DS-25 | `00-AUDITORIA.md` não aparece na lista de kinds da PARTE 1 nem na lista explícita de "não recebem frontmatter" | Fica **sem** frontmatter, e isso está declarado no `00-schema.md` | A PARTE 1 é exaustiva quanto ao que o painel lê; inventar um `kind: auditoria` seria criar contrato não especificado. Registrado por ser omissão, não decisão explícita do prompt |
| DS-26 | Em `kind: fases`, o prompt traz `paralelizavel` e `paralela_com`, mas a prosa da skill só tem "Roda em paralelo com: nenhuma" | "nenhuma" na prosa ⇒ `paralela_com: []` **e** `paralelizavel: false`; com fase declarada ⇒ lista preenchida e `paralelizavel: true` | Mapeamento único possível entre a prosa existente e os dois campos novos, sem mudar a prosa |
| DS-27 | Travessões (`—`) apareceram dentro de marcadores `{{...}}` no frontmatter do `TEMPLATE-tasks.md` | Substituídos por hífen ASCII dentro do bloco de frontmatter | O item 7 da verificação pede frontmatter sem acento; manter o bloco 100% ASCII elimina o risco de um caractere não-ASCII vazar para o arquivo gerado |

## Ajuste de compatibilidade com o OpenCode (instalação dupla)

Fatos verificados no binário do OpenCode v1.18.23 instalado na máquina (tabela de locais embutida na própria documentação do binário), não presumidos.

| # | Ambiguidade / achado | Decisão tomada | Motivo |
|---|---|---|---|
| DS-28 | Onde o OpenCode procura skills, e se seria preciso manter duas cópias da skill | O OpenCode **auto-carrega** skills de `~/.claude/skills/<name>/SKILL.md` (as chama de *external skills*). Na instalação global a skill é instalada **uma só vez**, em `~/.claude/skills/sprintx/`, e serve aos dois harnesses | Verificado na tabela de locais embutida no binário. Duplicar a pasta criaria duas fontes divergindo com o tempo — o pior defeito possível para uma skill cujo contrato é o produto |
| DS-29 | Não existe ponte `.claude` → `.opencode` no escopo de projeto | Na instalação de projeto a skill é copiada de fato para `.opencode/skills/sprintx/`, além de `.claude/skills/sprintx/` | A auto-carga externa vale para `~/.claude/` (global), não para o `.claude/` do projeto; sem a cópia, o OpenCode não enxergaria a skill no projeto |
| DS-30 | Projetos vizinhos usam ora `command/` ora `commands/`; qual é o correto | Ambos funcionam (`.opencode/command(s)/`, `~/.config/opencode/command(s)/`); adotado o **singular** `command/`, que é a forma do exemplo do próprio binário | Verificado no binário. Registrado porque a divergência entre projetos sugeria erro onde não há |
| DS-31 | `argument-hint:` do frontmatter dos commands não existe no OpenCode | Os commands do OpenCode são gerados a partir dos do Claude Code removendo apenas essa linha; o corpo e o `$ARGUMENTS` são idênticos | `$ARGUMENTS` é suportado pelos dois (verificado no binário). Manter fonte única e remover um campo é mais seguro que manter sete arquivos escritos duas vezes à mão |
| DS-32 | Como espelhar a skill no repositório sem duplicar a fonte: symlink `.opencode/skills/sprintx` → `.claude/skills/sprintx`? | Descartado o symlink; o repositório versiona só `.claude/skills/sprintx` (fonte única) + `.opencode/command/`, e o instalador materializa as cópias | Symlink quebra em clone no Windows e em download por zip — frágil demais para o caminho de instalação, que precisa funcionar em qualquer máquina |
| DS-33 | O corpo da skill precisaria de variante por harness? | Não: verificado que a skill não cita `.claude` em lugar nenhum e só usa caminhos relativos à própria raiz, então os mesmos arquivos servem aos dois sem alteração | Confirma a promessa que o README já fazia ("pode ser movida sem quebrar nada"); nenhuma regra ou contrato do método precisou mudar por causa do OpenCode |
| DS-34 | O instalador poderia sobrescrever trabalho do usuário ao reinstalar | `install.sh` é idempotente (verificado: segunda execução produz árvore byte a byte idêntica), tem `--dry-run`, e só toca `skills/sprintx/` e os sete `sprintx*.md` — nunca outros arquivos do usuário | Instalador que apaga o que não é dele é defeito grave; o escopo estreito torna a reinstalação segura |

## Referência cruzada com a runx (metade Run do método Expx)

| # | Ambiguidade / achado | Decisão tomada | Motivo |
|---|---|---|---|
| DS-35 | Como referenciar a runx sem inventar o que ela é | Li o README e o `references/00-schema.md` da runx e espelhei a seção "Build e Run" com a mesma tabela comparativa e a mesma frase de fecho ("Muda o gatilho e o tamanho. Nunca o rigor.") | As duas metades precisam ler como um método só; texto espelhado é reconhecível de um repositório para o outro. A runx já referenciava a sprintx — a referência agora é recíproca |
| DS-36 | **Achado de verificação:** o README da runx afirma que os kinds compartilhados são "idênticos campo por campo", e eu tinha copiado essa afirmação | Comparei os dois schemas com parser: os 6 kinds batem no topo, mas a task da runx tem `teste_regressao` a mais. O texto foi corrigido para "os mesmos campos e enums, com a diferença de `teste_regressao`" | Publicar "idêntico campo a campo" seria uma afirmação falsa sobre o contrato — exatamente o tipo de imprecisão que o expx-schema existe para eliminar |
| DS-37 | `teste_regressao` deveria ser acrescentado também à task da sprintx, para igualar os contratos? | Não. A sprintx segue com os 10 campos do seu contrato + os 3 de execução | Uma feature nova não tem comportamento errado anterior a provar; o campo seria sempre nulo. Além disso, mudar o contrato da task violaria a regra de ouro do ajuste anterior (o contrato do SKILL.md vence) |
| DS-38 | Onde registrar que o schema é compartilhado, para não divergir com o tempo | Seção "Contrato irmão" no `references/00-schema.md`, com a regra: mudança em kind compartilhado vale para as duas skills; kind exclusivo evolui sozinho | O `00-schema.md` é o arquivo que alguém abre para alterar o contrato — o aviso tem que estar lá, não só no README |
